# SHIMS — registre des substitutions & contraintes de chargement

Principe (voir [`PRINCIPLES.md`](PRINCIPLES.md) §2) : **un shim doit être fonctionnel**. On
ne répond jamais « oui oui » au jeu. Ce fichier liste tout ce qui n'est pas le comportement
natif d'origine, avec fidélité et risque. Légende : **RÉEL** (équivalent), **PARTIEL**,
**NO-OP**, **FACTICE**.

## Contraintes de chargement du bytecode (décisions de build, pas des shims)

| Élément | Détail / justification |
|---|---|
| **Reframe `game.jar` → `game-framed.jar` (ASM `COMPUTE_FRAMES`) — remplace `-Xverify:none` côté serveur** | Le bytecode **dex2jar** de `game.jar` n'a pas les *stackmap frames* exigées par le vérificateur Java 7+ (`VerifyError: Expecting a stackmap frame`). Sous `-Xverify:none` la JVM calcule paresseusement les *oop-maps* au **GC** via l'ancien `generateOopMap.cpp`, qui **PLANTE par intermittence** (`fatal error: Illegal class file … in method getDefaultStats`, **SIGABRT non déterministe** — déclenché quand un GC scanne une frame de `ConstantStats.getDefaultStats`/perks de guilde ; ~1 run/8 en test). C'est un **crash JVM réel, pas un bug de logique** (le serveur AUTORITATIF y est exposé aussi, pas que les tests). **Correctif durable APPLIQUÉ (2026-07-16)** : `tools/reframe/ReframeJar` (ASM 9.7, `COMPUTE_FRAMES`) réécrit les **64 196** classes de `game.jar` avec des frames valides → vérificateur rapide par table, **plus de `generateOopMap`**, et on **RETIRE `-Xverify:none`**. `desktop-port/run-online.sh` (serveur) et `server/smoke/run.sh` reframent à la demande et tournent sous vérification par défaut (`libs/game-framed.jar`, gitignoré/régénérable — comme `game-logic-framed.jar` côté client). **Sémantique inchangée** (métadonnées de vérif seulement) : vérifié `ResourceTest`/`CampaignAttackTest`/`CampaignPersistTest` identiques + boot serveur OK + `ChargeTest` **15/15 sans abort** (vs abort intermittent avant). On garde `-XX:TieredStopAtLevel=1` (C1 seul) par prudence (le C2 plantait sur le bytecode dex2jar). **Normalisation `itf` des `INVOKESTATIC` (ajoutée 2026-07-16, nuit 3)** : dex2jar émet parfois un `INVOKESTATIC` vers une méthode **statique d'INTERFACE** (ex. les lambdas R8 `$r8$lambda$…` d'interfaces comme `FXHandle`) encodé en `Methodref` au lieu d'`InterfaceMethodref` → la JVM lève `IncompatibleClassChangeError` (« must be InterfaceMethodref constant ») **à la résolution du lien** (au 1ᵉʳ appel, pas au chargement — d'où l'invisibilité jusqu'à ce que `HeadlessCombat` exerce ce chemin). `ReframeJar` corrige `itf = isInterface(owner)` pour les `INVOKESTATIC` (règle JVMS ; **non-sémantique**, §1). Vérifié : débloque le vrai `HeadlessCombat` headless (spike Opt.2 → `DONE`/WIN). **Extension `itf` `INVOKEINTERFACE` + `INVOKESPECIAL` de super-interface DIRECTE (ajoutée 2026-08-03, g54)** : le même défaut dex2jar touche aussi l'appel d'une méthode `default` d'interface. **Cas trouvé EN JEU (combat de guerre, g53)** : `SimpleStudiedBuff implements IStudiedBuff` appelle `IStudiedBuff.super.spawnParticles(Entity)` (méthode `default`) via `INVOKESPECIAL`, mais dex2jar l'encode en `Methodref` de classe → `IncompatibleClassChangeError: … IStudiedBuff.spawnParticles must be InterfaceMethodref constant` à la résolution du lien (1ᵉʳ appel, en combat quand le buff « étudié » d'un héros émet ses particules → **planterait TOUT combat** alignant ce héros ; la guerre l'a exposé la première en alignant 14 héros). **Correctif** : `ReframeJar` pose désormais (a) `INVOKEINTERFACE` → `itf=true` (JVMS 6.5 : toujours un `InterfaceMethodref`) ; (b) `INVOKESPECIAL` → `itf=true` **UNIQUEMENT si l'owner est une super-interface DIRECTE de la classe visitée** (`this.interfaces`, forme légale `T.super.m()`). ⚠️ **La restriction à la super-interface DIRECTE est essentielle** : JVMS 4.9.2 exige l'appartenance directe, et flip­per un `INVOKESPECIAL` vers une super-interface **indirecte** casse la vérif (`VerifyError: interface method reference is in an indirect superinterface`, vu sur `PegasusSkill3` → `IRampageAbility`, interface héritée via la super-classe donc **non** directe — laissée intacte par le garde-fou). `INVOKEVIRTUAL` jamais touché (owner jamais une interface). **Non-sémantique** (§1 : seul le type de l'entrée de constant pool change, pas l'appel). **Vérifié** : `SimpleStudiedBuff` → `InterfaceMethod` (corrigé), `PegasusSkill3` → `Method` (intact), les deux + `IStudiedBuff` **verify+link OK sous le vérificateur par défaut** (aucun `VerifyError`) ; régression **78/78** inchangée. **⚠️ `HeadlessCombat` ne reproduit PAS** le bug (la SIMULATION ne rejoue pas les VFX → `spawnParticles` jamais appelé ; A/B : ancien ET nouveau jar terminent `DONE`) → le crash est **rendu-seulement** (`AttackScreen` appelle `IBuffVFX.spawnParticles` chaque frame sur les buffs actifs). **✅ VÉRIFIÉ EN JEU (2026-08-03)** : attaque de guerre (guerre #4 ACTIVE, salle `REDUCE_ATTACKER_HP_FLAT`) → **combat RENDU joué de bout en bout sur les 3 équipes → écran RESULTS** ; **Baymax** (équipe 1) ET **Stitch** (équipe 3), les deux poseurs de `SimpleStudiedBuff`, ont casté avec leurs particules ; **compteur de crash `spawnParticles` = 0** (setup via l'outil DEV `WarWitnessSetup`). Détail : `JOURNAL.md` g54. |
